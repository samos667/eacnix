# Findings

Evidence behind the design in the [README](../README.md): what the pinned
Fedora artifacts contain, what the TPM measured in the VM tests and on real
hardware, and the analysis of Fedora's signed grub. Every entry says how it
was obtained and when.

## Pinned Fedora 45 artifacts

`pkgs/fedora/sources.nix` pins kernel `7.2.11-300.fc45`, grub `2.12-81.fc45`,
and shim `16.1-7` from Fedora's Koji. They were inspected on 2026-10-21.

- **shim** (`shimx64.efi`) is signed by Microsoft (Windows UEFI Driver
  Publisher, UEFI CA 2011, UEFI CA 2023 signer, UEFI CA 2023), so it boots on
  firmware that trusts either the 2011 or the 2023 CA.
  - Its `.vendor_cert` is `fedoraca` (Fedora Secure Boot CA 20200709), valid
    until 2037. It has no vendor dbx.
  - SBAT: `shim,4`.
- **grub** is signed twice during Fedora's CA rotation: by
  `fedora-signer-20250530` (Fedora Secure Boot CA 20250530) and by
  `kernel-signer` (`fedoraca`). shim accepts the second.
- **vmlinuz** is signed by `kernel-signer` (`fedoraca`).
- **Modules (4752)** are signed with PKCS#7/SHA-512 by "Fedora kernel signing
  key", a per-build key built into that build's kernel, so they only load on
  the exact `vmlinuz` they came with. They're xz-compressed after signing, so
  the signature sits inside the `.ko.xz`. The RPMs don't include
  `modules.dep`; the package runs `depmod`, which only writes index files.
- The packaged outputs are byte-identical to the RPM contents: `bzImage`, all
  4752 modules, `shimx64.efi`, `mmx64.efi`, and `grubx64.efi`.

## Pinned Bazzite artifacts

`pkgs/bazzite/sources.nix` pins the kernel of Bazzite stable
`44.20261012.1` (`ghcr.io/ublue-os/bazzite:stable@sha256:5d49529c…`, label
`ostree.linux` = `7.2.9-ogc3.1.fc44.x86_64`). Inspected on 2026-10-22 by
exporting the images with `crane`, unpacking the RPMs, listing signatures
with `sbverify --list`, and scanning the decompressed `vmlinux` for X.509
certificates.

- **Where it comes from.** Bazzite's Containerfile installs the kernel from
  `ghcr.io/ublue-os/akmods:ogc-<fedora>-<kernel>` (`/kernel-rpms`): the
  Open Gaming Collective ("ogc") kernel, re-signed by Universal Blue. The
  same tag's `/rpms/kmods` holds Universal Blue's signed `xone`, `xpadneo`,
  `v4l2loopback`, `openrazer`, `vhba`, and `wl` modules. Each image is one
  layer, fetched by its OCI digest (`sha256:e0282fd2…` for the kernel).
  ghcr.io serves public blobs to any bearer token.
- **Tag retention.** On 2026-10-22 the oldest `ogc-44-*` tag was
  `7.1.3-ogc3.4`, while Bazzite's Containerfile default still named `7.0.9`,
  so old tags are pruned.
- **vmlinuz** carries two signatures, by the self-signed "ublue kernel"
  (Universal Blue, kernel signing, serial `7DF87AF5…`, valid until 2124) and
  "ublue akmods" certificates. `ublue-os-akmods-addons` installs "ublue
  kernel" as `akmods-ublue.der`: the MOK Bazzite asks users to enroll
  (`ujust enroll-secure-boot-key`). The package build checks it with
  `sbverify --cert`.
- **Built-in keys:** only "Build time autogenerated kernel key". In-tree
  modules (5037, uncompressed `.ko`) are signed with it; Universal Blue's
  kmods (`xone`) are signed with "ublue kernel", so they load only through
  the MOK.
- **Config:** no `LOCK_DOWN_IN_EFI_SECURE_BOOT` (Fedora sets it),
  so the kernel doesn't lock itself down under Secure Boot; eacnix's
  `lockdown=integrity` does. `IKCONFIG=y`, `BPF_LSM=y`, `SCHED_CLASS_EXT=y`,
  `NTSYNC=m`, `INTEGRITY_MACHINE_KEYRING=y`.
- **NVIDIA:** `ghcr.io/ublue-os/akmods-nvidia-open` has the same tag, with
  `kmod-nvidia` 615.78.08 and negativo17's userspace RPMs.
- **Proprietary NVIDIA and the LTS kernel** (inspected 2026-10-22, same
  way). Bazzite's build matrix (`.github/workflows/build.yml`) builds
  `bazzite-nvidia` with `kernel_flavor: ogc-lts` and `nvidia_flavor:
nvidia-lts`; only `-nvidia-open` images use the `ogc` kernel.
  `bazzite-nvidia:stable` (44.20261012.1, `sha256:3d13e825…`) runs
  `6.18.56-ogc1.1.fc44`. `akmods-nvidia-lts:ogc-lts-44-6.18.56-ogc1.1.fc44`
  holds `kmod-nvidia` 580.178.04: five `.ko.xz` with license "NVIDIA", signed
  with "ublue kernel", vermagic `6.18.56-ogc1.1.fc44.x86_64`. The LTS kernel
  (`akmods:ogc-lts-44-…`, layer `sha256:1a9a5304…`) is signed by the same
  certificate as the `ogc` one (byte-identical `akmods-ublue.der`, checked
  with `sbverify --cert`). nixpkgs' `legacy_580` is the same 580.178.04, so
  eacnix uses its hashes for the userspace.
- Bazzite boots through Fedora's shim and grub, so eacnix uses its pinned
  Fedora boot chain (fc45) for it.
- The packaged `bzImage` and all modules are byte-identical to the RPM
  contents.

### Epic's rules on MOKs and out-of-tree modules

From [The FPS Review](https://www.thefpsreview.com/2026/10/15/fortnite-is-coming-to-linux-via-easy-anti-cheat-linux-v2-which-needs-secure-boot-tpm-2-0-and-signed-kernels-steam-deck-isnt-supported-yet/)
(read 2026-10-22): "Epic also requires every enrolled Machine Owner Key to be
well-known", and "Out-of-tree modules, with NVIDIA's drivers named
specifically, must be built by an organization and signed with a well-known
key." Its list of well-known keys includes Fedora and Universal Blue. eacnix
used to forbid every MOK, and `eacnix-check` warned on out-of-tree modules;
both now follow these rules.

### Bazzite's `ujust check-anticheat`

Bazzite's check (ublue-os/bazzite PR #6065, merged 2026-10-16, read at merge
commit `f97f3d9` on 2026-10-22) checks the running kernel's Authenticode
signer (`sbverify --list`) and every MOK (`mokutil --export`) against
well-known authority names: Canonical's Master CA, Fedora Secure Boot CA,
Universal Blue, Debian, openSUSE, SUSE Linux Enterprise, Rocky Linux,
Microsoft's UEFI CA, and AlmaLinux. It fails when shim's validation is
disabled (`mokutil --sb-state`), names modules with taint `E`, treats a
missing `kexec_load_disabled` sysctl as kexec being absent, and skips the
IOMMU check on handhelds (Valve hardware or SMBIOS chassis types 30–32). It
counts any event in PCR 8, 9, 11, or 12 as measured boot. Epic's published
list says "IOMMU enabled with passthrough disabled (on non-handheld
devices)". `eacnix-check` now makes the same checks; see `CLAUDE.md`.

The kernel ignores image hashes in shim's MOK list: in Linux 7.2.9's
`security/integrity/platform_certs/keyring_handler.c`, `get_handler_for_mok`
returns a handler only for X.509 entries. Hashes only let shim boot those
exact binaries.

## Measured boot in the Secure Boot VM test

`checks.secure-boot-vm`, run on 2026-10-21 under OVMF with a generated PK,
Microsoft's KEK and db, and swtpm. `tpm2_eventlog` showed:

| PCR | What was measured                                                                                                                           |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 4   | Three EFI applications only: `\EFI\eacnix\shimx64.efi`, `\EFI\eacnix\grubx64.efi`, then the kernel (loaded by grub through shim).           |
| 7   | Secure Boot state, PK, KEK, db, and dbx. A `db` authority event for shim, plus shim's `SbatLevel` and its vendor certificate (`MokListRT`). |
| 8   | Every grub command (`grub_cmd: …`), including the full `kernel_cmdline` with `init=/nix/store/…/init`.                                      |
| 9   | Files grub read: `grub.cfg`, the BLS entry, the kernel, and the initrd.                                                                     |
| 14  | shim's `MokList`, `MokListX`, and `MokListTrusted` (all empty).                                                                             |

Without Secure Boot, grub loads the kernel itself instead of through shim, so
PCR 4 has no kernel event and PCR 9 is what records the kernel.

The kernel logs "locked down from command line" rather than "from EFI Secure
Boot", because the module's `lockdown=integrity` takes effect first. The
result is the same.

The test needs two boots. make-disk-image boots its builder kernel through the
same OVMF, so the image can't be built with Secure Boot on. The test boots
once without it, enrolls the keys into the VM's variable store with
`virt-fw-vars`, and boots again.

## Measured boot in the Secure Boot VM test (Bazzite)

`checks.secure-boot-vm-bazzite`, run on 2026-10-22: the same setup, with
Universal Blue's "ublue kernel" certificate added to shim's `MokList` by
`virt-fw-vars --add-mok` (shim's GUID) when Secure Boot was turned on.

- shim accepted Bazzite's kernel under Secure Boot through the MOK.
  `eacnix-check` passed every check except `iommu`: `mok` reported "shim's
  vendor certificate (fedoraca) and well-known MOKs: ublue kernel", and
  `measured-authority` the Microsoft UEFI CA 2011.
- PCR 4 held shim, grub, and the kernel, as on Fedora. PCR 7 held the `db`
  authority event for shim and three shim authority events (Fedora's run had
  two), the extra one presumably for the kernel's MOK approval.
- Fedora's grub sets `LoaderInfo` ("GRUB 2.12").
- The kernel logged "locked down from command line".
- NVIDIA (same test, with `eacnix.nvidia.enable` in the eac system):
  `kmod-nvidia` 615.78.08 from `akmods-nvidia-open` (five `.ko.xz`, each
  signed with "ublue kernel", no `intree`) was packaged byte-for-byte, with
  nixpkgs' 615.78.08 userspace. Under Secure Boot with the MOK enrolled, the
  kernel accepted `nvidia.ko`: `systemd-modules-load` and `modprobe nvidia`
  both ran its init ("NVRM: No NVIDIA GPU found", then ENODEV), and taint `E`
  stayed clear. Without shim the MOK never reaches the kernel, so a direct
  kernel boot can't load these modules.
- Proprietary NVIDIA (`checks.secure-boot-vm-bazzite-lts`, same day):
  `eacnix.nvidia.flavor = "proprietary"` moved the eac path to the LTS
  kernel `6.18.56-ogc1.1.fc44`. Under Secure Boot with the MOK enrolled, the
  kernel accepted `kmod-nvidia` 580.178.04 (license "NVIDIA"): `modprobe
nvidia` ran its init ("NVRM: No NVIDIA GPU found"). `eacnix-check` passed
  every check except `iommu`, with the kernel "signed under 'Universal Blue'".
  No pre-Turing GPU was available, so the driver itself is untested.
  `checks.kernel-vm-bazzite-lts` boots that kernel directly with the same
  results as `kernel-vm-bazzite` below.
- `checks.kernel-vm-bazzite` (direct kernel boot, same day): in-tree modules
  load under `lockdown=integrity`, a stripped one is refused, and `scx_lavd`
  takes over.

## lanzaboote next to eacnix (VM)

`checks.lanzaboote-vm`, run on 2026-10-21: OVMF with lanzaboote's test PK as
PK and KEK, Microsoft's KEK and db, and lanzaboote's test db certificate added
to `db`, with Secure Boot enforcing and swtpm.

- lanzaboote's normal entry (its stub and UKI, signed with the owner's key)
  boots under Secure Boot.
- The eac path boots through Fedora's shim on the same firmware.
  `eacnix-check` passes every check except `iommu` (QEMU has no IOMMU).
  `measured-authority` shows the Microsoft UEFI CA approving shim, so the
  measured chain is Microsoft-approved even with the owner's certificate in
  `db`. The full `db`, owner's key included, is still measured into PCR 7;
  whether EAC accepts that is unknown.
- On real hardware (the MSI board below, 2026-10-22), the `eac` UKIs came
  back after being hidden: lanzaboote's `prepare-sb-auto-enroll` service
  re-signs the ESP by running `lzbt` directly at boot, bypassing NixOS's
  install hook. eacnix now runs `eacnix-boot hide` after that service and
  after `auto-cryptenroll`, which does the same; the VM test covers it.
- lanzaboote builds a UKI for every specialisation
  (`EFI/Linux/nixos-generation-<n>-specialisation-eac-<hash>.efi`); eacnix
  deletes it after each install.
- lanzaboote creates no `Boot####` entry; it relies on the firmware's fallback
  path. When the test's disk image is built, BootOrder holds only OVMF's
  internal apps (boot menu, firmware setup), so appending "NixOS EAC" would
  have made it the default boot. eacnix appends only behind another OS entry,
  which the firmware creates on the first boot.

### OVMF and boot entries

Observed in the VM tests, not on real hardware:

- OVMF drops a `Boot####` entry that neither BootOrder nor BootNext
  references. A "NixOS EAC" entry created while building the image without
  `addToBootOrder` was gone at first boot. The MSI board below kept such an
  entry.
- OVMF appends its own auto-created entries (fallback device, internal apps)
  to BootOrder at boot, after anything already there.

## Hardware: MSI MAG X870 Tomahawk WIFI

BIOS 1.A92, AMD CPU, Radeon RX 7900-series GPU (Navi 31). Fedora 7.2.11-300.fc45 booted via
`eac-reboot` on 2026-10-21. EAC version: not released. Hardware-verified from
the TPM event log and sysfs, and with `sudo eacnix-check`.

- **Boot path:** `BootCurrent` was "NixOS EAC" (`\EFI\eacnix\shimx64.efi`),
  `LoaderInfo` was `GRUB 2.12`, and `BootNext` was consumed while `BootOrder`
  stayed unchanged.
- **PCR 4:** `\EFI\eacnix\shimx64.efi` → `\EFI\eacnix\grubx64.efi` → the
  kernel, as in the VM.
- **PCR 8/9:** grub's commands, `grub.cfg`, the BLS entry, the kernel, the
  initrd, and the kernel command line. The command line contains
  `init=/nix/store/…-nixos-system-<hostname>-…/init`, so the hostname and the
  fact that this is NixOS are visible in the measurements.
- **Keys:** stock MSI factory keys. PK is `MSI SHIP PK`; KEK holds Microsoft's
  2011 and 2023 KEKs and `MSI SHIP KEK`; `db` holds Microsoft's Windows PCA
  2011, UEFI CA 2011 and 2023, Option ROM CA 2023, and `MSI SHIP DB`; `dbx`
  holds 431 hashes.
- **MOK:** `MokListRT` holds only `fedoraca`. `eacnix-check` compared it byte
  for byte with the certificate in the pinned shim.
- **Lockdown, kexec, BPF LSM, Secure Boot (user mode), TPM 2.0:** all pass.
- **Firmware settings matter.** With the board's initial settings,
  `eacnix-check` warned twice:
  - no `db` authority event for shim in PCR 7. The firmware's Image
    Execution Policy let images run without verification (it also booted an
    unsigned systemd-boot with Secure Boot "enabled");
  - "DMA Protection Disabled" in PCR 7: pre-boot DMA protection was off.

  After changing both in the BIOS, the firmware logged
  `db → Microsoft Corporation UEFI CA 2011` for shim, and the DMA event was
  gone. Both checks pass.

- **Remaining warning, IOMMU:** 37 of 38 IOMMU groups are translated, but the
  GPU's group is in `identity` (passthrough) mode despite
  `iommu.passthrough=0`. This is upstream AMD IOMMU driver behaviour, not
  specific to this machine: `amd_iommu_def_domain_type()` forces an identity
  domain on every PASID-capable device when SME/SNP is off, and recent AMD
  GPUs support PASID (amdgpu uses it for compute). AMD's series
  "iommu/amd: Fix default domain selection for PASID-capable devices"
  (Vasant Hegde) limits forced identity to GPUs with known hardware bugs
  (early Raven/Picasso APUs, Radeon Pro WX 4100), so discrete GPUs get a
  paging domain. It was accepted for linux-next on 2026-09-24; the mainline
  release that carries it isn't confirmed. Fedora 7.2.11 predates it.
  Sources: [series](https://ratatoskr.run/linux-iommu/2026/07/17307944/t),
  [v2 patch](https://ratatoskr.run/linux-iommu/2026/08/17452208/t).

## Fedora's signed grub

From `grub2-efi-x64-2.12-87.fc46.x86_64.rpm` (static analysis on 2026-10-21;
the pinned 2.12-81.fc45 build behaves the same in the VM tests).

- **Embedded config:** none. The image holds only a prefix, `/EFI/fedora`,
  and a memdisk with `fonts/unicode.pf2`. Red Hat's patches (`fw_path`) make
  grub look for `grub.cfg` in the directory it was started from first. The
  Secure Boot VM test confirms this, so eacnix uses `EFI/eacnix/` and doesn't
  collide with a real Fedora install.
- **SBAT:** `grub,5` and `grub.rh,2`.
- **Built-in modules (116).** Under Secure Boot grub can't load modules from
  disk, so this set is all there is. The ones that matter:
  - `tpm`: grub measures the kernel, initrd, and command line into PCR 8/9.
  - `blscfg`, `blsuki`: grub reads BLS entries. Fedora's `blscfg` calls a
    `load_video` function that only Fedora's own `grub.cfg` defines, so
    eacnix's `grub.cfg` defines it too.
  - Filesystems: `fat`, `ext2` (also reads ext4), `btrfs`, `xfs`, `f2fs`,
    `hfsplus`, `iso9660`, `squash4`. No `zfs`.
  - Storage: `luks`, `luks2`, `cryptodisk`, `lvm`, `mdraid09`, `mdraid1x`.
    There is no argon2, so LUKS2 volumes with the default key derivation
    probably can't be unlocked by grub. eacnix keeps kernels on the ESP, so
    this doesn't affect it.

To reproduce the module list, parse the PE `mods` section: a
`grub_module_info64` header followed by module records. Read each ELF module's
`.modname`, plus the prefix, config, and memdisk records.

## Fedora's kernel configuration

From the vendored config (`pkgs/fedora/kernel-config`, 7.2.11-300.fc45):

| Option                                                       | Value                                                | Meaning for eacnix                                                                                                          |
| ------------------------------------------------------------ | ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| `CONFIG_LSM`                                                 | `"lockdown,yama,integrity,selinux,bpf,landlock,ipe"` | NixOS overrides it with `lsm=` from `security.lsm`, which always includes `bpf`. Lockdown is an early LSM and stays active. |
| `CONFIG_LOCK_DOWN_IN_EFI_SECURE_BOOT`                        | `y`                                                  | Lockdown turns on automatically under Secure Boot.                                                                          |
| `CONFIG_MODULE_SIG`, `CONFIG_MODULE_SIG_ALL`                 | `y`                                                  | Modules are signed; lockdown enforces it (`MODULE_SIG_FORCE` is unset).                                                     |
| `CONFIG_INTEGRITY_MACHINE_KEYRING`                           | `y`                                                  | MOK keys are trusted for module signatures, which is why any enrolled MOK breaks the trust chain.                           |
| `CONFIG_INTEGRITY_PLATFORM_KEYRING`, `CONFIG_LOAD_UEFI_KEYS` | `y`                                                  | Firmware `db` keys go to `.platform`, used only for kexec, which is disabled.                                               |
| `CONFIG_KEXEC`, `CONFIG_KEXEC_FILE`                          | `y`                                                  | kexec is built in, so the sysctl is required.                                                                               |
| `CONFIG_INTEL_IOMMU_DEFAULT_ON`                              | not set                                              | eacnix passes `intel_iommu=on`.                                                                                             |
| `CONFIG_IKCONFIG`                                            | not set                                              | No `/proc/config.gz`; see `eacnix.kconfigServices`.                                                                         |
| `CONFIG_SCHED_CLASS_EXT`, `CONFIG_DEBUG_INFO_BTF`            | `y`                                                  | sched_ext schedulers work.                                                                                                  |
