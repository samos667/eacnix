# eacnix

NixOS module that boots NixOS userspace on a vendor-signed kernel (Fedora or
Ubuntu) through the vendor's shim and grub, so the system meets EAC Linux v2's
Secure Boot and measured boot requirements. Read `README.md` for the
requirement table, the design, and the questions for Epic; `docs/findings.md`
for the evidence behind them.

## Design invariants

- **Vendor artifacts stay byte-identical.** The kernel, `.ko` modules, shim,
  and grub are signed. Their derivations unpack only (`dontFixup = true`).
  Module signatures sit inside the `.ko.xz`, so only changes to the
  decompressed bytes break them. Verify by comparing hashes with the RPM
  contents.
- **Evaluation reads vendored files, never build outputs (no IFD).**
  `pkgs/fedora/kernel-config` and `kernel-modules.list` are generated by
  `.#fedora-kernel.vendored`, and the kernel build fails if they drift. Fix a
  drift by regenerating them; editing them by hand doesn't help.
- **Everything in the `eac` specialisation comes from the vendor.** Every
  kernel module is vendor-signed, and every boot-chain binary
  (shim, grub, kernel) is a vendor binary. Enforce this with assertions
  (`boot.extraModulePackages`, `boot.kernelPatches` empty).
- **Pin related artifacts together.** Shim, grub, and kernel are pinned by
  hash from the same vendor release, and the update script bumps them as a
  set.
- **ESP ownership is explicit.** `EFI/<eacnix.boot.directory>` belongs to
  this module; lanzaboote/systemd-boot paths belong to them. Write only inside
  paths this module owns. The one exception: `--hide-systemd-boot-entries`
  deletes systemd-boot entries whose `init=` is an eac system, matched by
  content (systemd-boot names entries by content hash), and never touches
  anything else in `loader/entries`.
- **No MOK, ever.** MokList is global and the vendor kernel trusts it for
  module signing, so any enrolled MOK fails EAC on every entry. Custom keys go
  only into the firmware `db`, next to Microsoft's, which stay enrolled.
- **Published requirements are the spec.** EAC v2 isn't released, so
  `eacnix-check` encodes Epic's published list one requirement at a time.
  Every module feature traces back to one of those requirements.
- **The ESP is never left half-written.** `eacnix-boot install` plans the
  whole install, prunes, checks free space, then copies. Each file goes in
  through a `.tmp` and a rename, and an entry is written only after its
  kernel and initrd. A failure leaves the previous entries bootable.
- **Switch with `BootNext`.** `eac-reboot` is a one-shot switch. eacnix
  touches BootOrder only when `eacnix.boot.addToBootOrder` asks it to, and
  then only appends its own entry if it's missing: it never reorders or
  removes anything. Firmware may append its own entries behind it, so "last"
  isn't an invariant; "once, and never moved" is.
- **Claims match evidence.** EAC behaviour that hasn't been tested (see the
  README's questions for Epic) gets written as unknown, in docs and in option
  descriptions. The README is user- and Epic-facing: keep it neutral and
  current. Detailed evidence (artifact analysis, PCR contents, hardware runs)
  goes in `docs/findings.md`, dated and with how it was obtained.

## NixOS kernel contract

A kernel in `boot.kernelPackages` has to satisfy what NixOS modules read from
it. When a NixOS change breaks evaluation, the fix usually belongs in
`passthru` in `pkgs/fedora/kernel.nix`:
- `target`, `version`, and `modDirVersion`;
- `config`, with nixpkgs' `isYes`/`isEnabled` helpers;
- `features`;
- `buildDTBs`;
- `src`, `patches`, and a `stdenv` with a compiler, for kernelPackages tools
  such as turbostat and cpupower that build from the kernel tree;
- `override` taking `kernelPatches`, `randstructSeed`, and `features`.

Userspace sometimes expects Fedora's filesystem layout around the kernel, not
just kernel features. The known case is libbpf's kconfig lookup
(`/boot/config-$(uname -r)`; Fedora has no `/proc/config.gz`), handled per
service by `eacnix.kconfigServices`. Fix such cases inside the eac
specialisation, scoped to the services that need them, without writing to the
ESP.

Defining `features` makes NixOS skip `system.requiredKernelConfig`, which is
why `modules/eacnix.nix` re-asserts it. `callPackage` fills `kernelPatches`
from `pkgs.kernelPatches` unless it's passed explicitly.

## eacnix-check

`pkgs/eacnix-check/eacnix-check.py` uses only the standard library and parses
the TCG2 event log binary itself. Each check id maps to one of Epic's published
requirements; keep it that way, and add a check when Epic publishes a new
requirement. Hardware differs from the VM: firmware may skip the PCR 7 `db`
authority event and log "DMA Protection Disabled", so those two are `warn`, not
`fail`. Without Secure Boot, grub loads the kernel itself, so PCR 4 has no
kernel event and PCR 9 is what proves the kernel was measured.

## Testing

`nix flake check -L` runs all VM tests. Pipe build output through
`set -o pipefail`, because `| tail` hides failures.

- `fedora-kernel-vm`: direct kernel boot. `lockdown=integrity` enforces module
  signatures without Secure Boot, and the test proves it by loading a module
  with its signature stripped. It also runs `scx_lavd` and checks that sched_ext is
  enabled, which covers `kconfigServices`.
- `secure-boot-vm`: firmware → shim → grub → kernel under OVMF and swtpm. The
  disk image has to be built without Secure Boot, because make-disk-image
  boots its builder kernel through the VM's OVMF and reads `OVMF.variables`,
  ignoring `virtualisation.efi.variables`. So the test boots once, enrolls
  keys into `machine.state_dir`'s vars file with `virt-fw-vars`, and boots
  again. Read the boot chain from `tpm2_eventlog`; `docs/findings.md`
  records what each PCR held.
  The test also checks `addToBootOrder`: the entry is listed once and never
  first, and after a simulated firmware reset drops it,
  `switch-to-configuration boot` appends it again without changing anything
  else. It also checks that systemd-boot's menu has no eac entry, and runs
  `eacnix-check --json` on both boots. In the VM the only expected failure is
  `iommu`, because QEMU has no IOMMU here.
- `esp-full`: `eacnix-boot` against a 24 MiB FAT image and fake generations.
  It checks that a full ESP fails before writing anything, that pruning makes
  room, and that `.tmp` leftovers get removed.

Real EAC attestation can only be checked on hardware with a protected game.
Record hardware results in `docs/findings.md`, marked as hardware-verified,
with the date, the board and firmware, the vendor kernel version, and the EAC
version.
